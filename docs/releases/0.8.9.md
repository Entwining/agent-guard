# v0.8.9

Credential stores are now refused wherever their clients keep them, not only under their default HOME spelling. Besides gh, glab, Cargo, AWS, Docker, kube and GnuPG, the guard protects Pi's `~/.pi/agent`, Codex's `~/.codex`, Claude Code's `~/.claude`, Snowflake CLI's `~/.snowflake` and `~/Library/Application Support/snowflake`, dbt's `~/.dbt` and pnpm's `~/Library/Preferences/pnpm`, in the directory a client's variable names in the hook's environment (such as `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `DOCKER_CONFIG` or `GNUPGHOME`), and wherever symbolic links lead a default directory. Only the credential files are protected, so `cat ~/.codex/config.toml` and `rg token ~/.codex/sessions` stay permitted.

Searching, copying or archiving a directory that holds a store is refused under the new `credential_store` reason, such as `rg token ~/.codex`, `rg token ~/.config/*` or `cp -R ~/.claude /tmp/claude`, unless name filters bound the walk to names that select no credential file, such as `rg -g '*.lua' foo ~/.config`. `rg foo ~/.claude` stays permitted because ripgrep skips the hidden `.credentials.json` without `--hidden`. `rg` without a path now searches the pipe that feeds it instead of the working directory, and a `find` that passes only `-type f` names to `xargs rg` keeps its name filter.

Moving a store directory is refused unless it lands on another store location that protects the same credential files, so `mv ~/.config/glab-cli ~/Library/Application\ Support/glab-cli` is permitted and `mv ~/.codex ~/backup/codex` is not.

A store variable set only in a shell profile the consumer did not load, or spelled with `~`, is not followed, and a command option such as dbt's `--profiles-dir` does not move a store; add such a directory to the consumer's read restrictions, as the [known limits](https://github.com/Entwining/agent-guard/blob/v0.8.9/docs/setup.md#what-a-command-does-when-it-runs) describe.
